BayanihanHub — Bug Fixes, Features & Notification System
Inspect the existing BayanihanHub project first and implement all changes directly in the current architecture.
Core Rules
Preserve existing functionality.
Reuse existing frontend components, backend APIs, database models, authentication, notification system, and email infrastructure.
Do not replace real data with mock frontend data.
Do not hard-code user IDs, post IDs, or email addresses.
Fix root causes instead of hiding layout problems.
Backend must enforce authorization and ownership.
Do not expose backend errors, stack traces, passwords, tokens, or private data to users.
Keep the UI consistent with the existing BayanihanHub design.

2. Bug Fix — Favorite/Heart Toggle
The Browse Dashboard currently has incorrect favorite behavior.
Fix the state logic completely.
If the post is not saved
When the user clicks the heart:
API → Save item successfully
→ Heart becomes active/filled
→ Show "Added to favorites"
If the post is already saved
When the user clicks the heart:
API → Remove item successfully
→ Heart becomes inactive/uncolored
→ Show "Removed from favorites"
Requirements:
Initialize the heart from the actual backend saved/favorite state.
Do not assume the initial state.
Update the icon only after a successful API operation.
If the API request fails, restore the previous state.
Prevent duplicate/rapid requests.
Prevent contradictory toast messages.
Correctly update the state after page refresh.
Correctly update the state when browsing paginated/infinite-scroll results.
Keep Browse, Item Details, and Saved Items synchronized.
Use the existing saved/favorite database relationship.
The message and icon state must always describe the same action.

User is authenticated.

Deletion
Use the existing soft-delete/removal mechanism if available.
After deletion:
Remove the post from Browse.
Remove it from public search.
Remove it from active listings.
Preserve required audit information.

Admin Removed

7. Admin Ratings Tab
Improve the Admin Panel's Ratings tab.
The Admin should be able to view the ratings associated with a user in a clear and organized manner.
User Rating View
For each user, display:
User name.
Profile image where permitted.
Overall rating/average.
Total number of ratings.
Individual ratings.
Rating value.
Reviewer information according to existing privacy rules.
Review/comment where applicable.
Date of rating.
Related transaction/exchange if available.
Sorting
Allow Admin to view ratings:
Highest → Lowest
Lowest → Highest
Newest → Oldest
Oldest → Newest
The default view may show the most relevant aggregate information, while allowing the Admin to inspect the individual ratings.
Do not calculate ratings incorrectly from only the currently visible/paginated records.
Use backend aggregation where appropriate.
Moderation Safety
Ratings should be information available to Admins for moderation review, not an automatic ban mechanism.
Do not automatically ban or suspend a user solely because their rating falls below a hard-coded threshold.
If the existing moderation system allows Admin action after reviewing a user's history, provide the appropriate existing moderation controls, such as:
Review user.
View reports.
View rating history.
Suspend.
Restrict.
Remove, where already supported.
Any suspension/removal must continue to use the existing authorization, confirmation, reason, and audit-log system.

10. Security Email — Password Reset
Implement/test a secure password reset email.
Flow:
Forgot Password
→ User enters email
→ Secure reset token generated
→ Email sent
→ User opens reset link
→ Token validated
→ New password submitted
→ Token invalidated
Requirements:
Token must be cryptographically secure.
Token must expire.
Token must be single-use.
Do not store plaintext reset tokens if the architecture supports secure hashing.
Do not expose tokens in logs.
Do not reveal whether an email belongs to an account through an overly specific response.
Invalidate the token after successful password reset.
Invalidate previously active reset tokens where appropriate.
