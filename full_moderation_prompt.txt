# MVP ADD-ON — REPORTING & ADMIN MODERATION SYSTEM

## Objective

Add a complete **Report** system to BayanihanHub so users can report problematic **posts/items, community requests, and other users**, while Admins can review reports and take appropriate moderation actions.

The system must connect directly to the existing **Admin Dashboard, Users, Posts, Requests, Reports, Notifications, and Audit Logs** systems.

**Do not create a separate moderation system if one already exists. Extend the existing implementation.**

---

# 1. Add Report Button

Add a **3-dot action menu** or **Report** button wherever appropriate.

### On Posts / Donation Items

Example:

```text
[ ❤️ Save ] [ Request Donation ] [ ⋮ ]

                         └── Report Post
```

The **Report Post** option should be available to users viewing another user's post.

### On User Profiles

Add:

```text
[ ⋮ ]

   Report User
   Block User
```

Do not allow users to report themselves.

# 14. Reporter's Privacy

**Never reveal the identity of the reporter to the reported user.**

For example, do not send:

> "John reported your post."

> "Your post was reported and reviewed by BayanihanHub administrators."

Reporter information should only be available to authorized Admins.

# 15. Duplicate Report Prevention

Prevent abuse of the report system.

A user should not be able to repeatedly submit hundreds of identical reports against the same target.

Implement reasonable duplicate prevention, for example:

```text
Same user
+
Same target
+
Same report reason
+
Existing pending report
```

should normally reuse or prevent another duplicate report.

Do not completely prevent users from submitting legitimate future reports if the situation changes.


# 25. Important Security & Privacy Rules

**DO NOT:**

* Reveal the reporter's identity.
* Allow users to report themselves.
* Allow normal users to execute Admin actions.
* Delete moderation evidence immediately.
* Allow unlimited duplicate reports.
* Trust frontend-only authorization.
* Create duplicate moderation systems.
* Automatically suspend users simply because they were reported.

**DO:**

* Preserve moderation evidence.
* Require Admin review.
* Log Admin actions.
* Require reasons for moderation actions.
* Notify affected users appropriately.
* Enforce permissions on the backend.
* Reuse existing BayanihanHub systems.

# Final Goal

Turn BayanihanHub's reporting feature into a proper **community moderation workflow**:

> **Users report → Admin investigates → Admin takes action on the post/user → affected user is notified → action is audited → report is resolved.**

The key requirement is that **reporting must not be a dead-end form**.

A report must give Admins enough information and tools to actually take action against the **reported post, request, or user**, while preserving privacy, security, auditability, and the existing BayanihanHub architecture.


Feature: Persistent Floating Settings Navigation

User Story
As a user, when I'm inside the Settings section (on the main list or any sub-page like Notifications or Privacy & Trust), I want the settings navigation menu to stay accessible so I can jump between sections without scrolling back up or tapping "back" repeatedly.

Problem
Currently the settings nav list (Profile & Location, Community Discovery, Notifications, Privacy & Trust, Messaging, Account & Security, Appearance, Data & Privacy, Danger Zone) is likely a static list — once the user scrolls down or navigates into a sub-page, it's gone from view.

Requirements

Sticky positioning
The nav panel should use position: sticky (web) or an equivalent fixed/floating container (mobile) so it remains anchored within the viewport as the page content scrolls beneath it.
It should not overlap the top app bar/header.
Persistence across sub-pages
When a user taps into a sub-section (e.g., "Notifications"), the nav panel remains available — either as a collapsed floating button/handle that expands on tap, or as a persistent rail/drawer, so switching sections doesn't require backing out first.
Active state indicator
The currently active section keeps the highlighted state (green background + left accent bar, as in the current design) so users always know where they are.
Responsive behavior
Desktop/tablet: sidebar stays pinned to the left as a sticky column.
Mobile: collapse into a floating pill/FAB that expands into the full list on tap, or a bottom sheet — avoid permanently consuming vertical space on small screens.
Danger Zone stays visually distinct
Red text/icon treatment preserved regardless of container state (floating, collapsed, expanded).

Acceptance Criteria

 Scrolling settings content does not scroll the nav out of view.
 Nav remains reachable from any settings sub-page without a back navigation.
 Active item highlight updates correctly when switching sections via the floating nav.
 No visual overlap with header/status bar at any scroll position.
 Works at minimum down to a ~320px mobile viewport width.

Out of scope (MVP)

Drag-to-reorder nav items
Customizable/user-hidden sections
Animations beyond a basic expand/collapse transition
